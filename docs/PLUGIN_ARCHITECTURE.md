# Windows 插件化预案

状态：首个本地 `recognizer` 插件已落在 `plugins/session_recognition/`，由 `app/plugin_loader.py` 校验清单和宿主 API 版本后加载。标题 OCR、联系人匹配、同名消息核对和清未读辅助线索在插件中；宿主仅提供窗口采集、消息 OCR、只读快照接口和账号关联。打包后插件位于 EXE 旁，可单独替换，重启生效。自由排序、多插件编排、CRM 登录和 CLI 插件仍未实现。未确认身份时不生成回复或填入。

## 目标与参考

- 以小步、可验证的改动逐步加入桌面宿主扩展接口；之后在已有扩展类型内新增或升级插件，不必改 `core/engine.py` 或重新打包宿主 EXE。
- 插件各占 EXE 外的独立目录，可单独启用、禁用、排序和更新。新扩展类型或不兼容的接口变更仍可能需要升级宿主。
- 参考 DeerFlow 的公开扩展接口、受控插件列表、确定的加载顺序、版本兼容检查和独立升级；不照搬其服务端依赖或运行时。参考：https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/extensions/AGENTS.md

## 当前需要改造的边界

- `main.py` 目前一次只采集一个最近激活的 `hwnd`，切窗口会重启采集；`app/worker.py` 仍在同一个循环中采集和调用插件，但不再实现标题匹配规则。
- `app/settings.py` 只保存固定字段；加载器目前只校验并装载受控插件，没有插件列表、启停/排序配置或 CLI 命令分发。
- `app/plugin_api.py` 是宿主 API v1：插件通过它使用窗口 OCR 和只读本地快照，不依赖快照实现细节。`core/engine.py` 未改动。
- 同名候选手选由插件提供候选账号内 ID，宿主显示列表并发出用户确认命令，采集子进程复核窗口/账号/选中行后才采用；切换时失效，填入前再次核对。它不是自动识别证据，也不写入持久配置。

## 小步实施约束

- 不一次性重写 `main.py`、`app/worker.py` 或设置页；每一步只处理一个清晰边界，保留既有 OCR 行为和配置兼容性。
- 独立目录、公开合同和加载器已加入；下一步单独接入可排序策略。账号/窗口状态、登录门禁、CLI 分发仍是后续独立改动。
- 每一步都验证旧版单账号 OCR、候选生成和填入流程仍可用。仅在对应能力真正接入时才修改相关界面、打包配置和数据结构。
- CRM 登录与微信多开仍是后续能力；当前阶段只记录接口预留，不引入依赖、不改变启动流程，也不扫描微信进程。

## 宿主与插件合同

- 当前 `recognizer` 的 `plugin.json` 声明 `id`、`version`、`api_version: 1`、`capability: recognizer` 和 `entry`。入口导出 `read_window_context`（当前窗口 UIA 标题、可见消息及时间）、`read_header`（OCR 回退）、`Match` 和有 `needs_refresh`、`resolve_fast`、`resolve` 方法的 `Recognition`；`app/worker.py` 只通过加载器调用这些接口。短消息序列、OCR 放大取证、同名判断及清未读信号均由插件内部编排。
- 宿主 v1 服务在 `app/plugin_api.py`：`ocr_boxes`、`classify_chat_box`、`open_snapshot`、`snapshot_stamp`、`snapshot_text`。插件不得自行连接微信原始 DB；`open_snapshot` 只面向本地已发布的明文副本。
- 源码运行时从仓库 `plugins/` 加载；发布包从 EXE 同级 `plugins/` 加载。替换插件后重启生效，清单版本不兼容或入口缺失时采集停止并显示错误，不回退到未确认的旧会话。
- 宿主负责插件发现、生命周期、配置、任务调度、会话身份、登录门禁、界面和 CLI 分发；插件只能通过版本化的公开合同贡献能力，不直接依赖宿主内部模块。
- 每个 `plugins/<id>/` 目录包含清单和入口。清单至少声明稳定 ID、插件版本、兼容的宿主 API 版本、扩展类型、入口及配置模式；加载前检查 ID 冲突和版本兼容。
- 预留四类扩展：`recognizer`（识别当前会话）、`message_source`（读取消息）、`auth_provider`（助手登录）、`command`（CLI 命令）。设置页入口由宿主提供，插件贡献配置字段和校验规则。
- 识别策略返回账号/窗口/会话候选、依据和状态（唯一匹配、无法确定、失败）；宿主按用户配置的插件顺序尝试，并复用同一次采集的 OCR/窗口观察结果。插件失败不得复用上一个窗口或账号的识别结果。
- 插件列表及识别顺序由用户配置。安装、启用与升级分别管理；可选识别插件加载失败时显示原因并继续下一策略，设为必需的登录插件无法使用时不得启动受保护功能。
- CLI 插件命令必须在 GUI 初始化前分发。将来配置为必需登录后，CLI 的受保护命令也要经过同一登录门禁。
- 插件更新先在独立暂存目录验证清单和兼容性，再替换插件版本；失败恢复旧版本。更新不得清空插件配置或账号缓存。首版可以要求重启程序生效，不要求热替换。
- 外部插件的 Python 依赖或本地二进制库需要随插件包提供，或由宿主明确声明为公共依赖；不能假设 PyInstaller 自动收集后来加入的模块。

## 登录与微信多开

- CRM 等登录方式属于助手的 `auth_provider`，不是微信登录。本阶段只预留接口，不连接 CRM。将来启用必需登录时，认证成功后才启动会话采集和回复；退出或登录失效时停止这些功能。
- 分开保存助手用户身份、微信账号身份、微信窗口身份和会话身份。聊天记录和候选回复按 `(wechat_account_id, conversation_id)` 隔离，窗口运行状态按 `hwnd` 隔离；显示名称、PID 和 HWND 都不能单独充当持久账号 ID。
- 枚举全部微信窗口，跟随最近操作的微信窗口。优先根据窗口进程及关联进程实际打开的 `db_storage` 文件，将窗口关联到微信账号；同一账号的多个窗口仍分别跟踪当前会话。
- 进程证据不足或出现多个候选账号时，继续使用当前窗口的标题、可见消息和候选账号消息库核对。无法唯一确定时标记该窗口为待识别，继续观察，不把其他账号的历史或候选回复显示、填入该窗口。
- OCR 模式没有数据库密钥时仍可工作：按当前窗口隔离临时会话状态，不把不同窗口里同名会话合并为一个持久 ID。关闭或重建窗口时重新核对映射。
- 填入前核对目标窗口和当前识别结果仍属同一个账号/会话。前台切换、窗口关闭和迟到的插件结果都必须使旧目标失效。

## 密钥与扫描边界

- 遵守根目录 `AGENTS.md`：默认 OCR；启动、登录、切账号、切会话、轮询、消息/WAL 更新、插件回退和密钥失效都不得自动扫描微信进程内存。只复用按微信账号保存的有效密钥。
- 密钥提取由宿主设置页的用户显式操作触发，独立于插件编排；失败或新库缺密钥只提示，不自动重试。一个用户操作至多启动一个扫描任务。
- 首版只加载受控插件。Python 插件若在同一权限下运行，可以绕开宿主接口自行调用 Windows API；清单里的能力声明不能充当强制隔离。开放任意第三方插件前，需另行设计进程及权限隔离。

## 待验证

- 用真实微信多开验证 `hwnd -> 进程组 -> db_storage` 是否能稳定一一对应，以及同账号多窗口、辅助进程和窗口重建的情况。
- 验证同名联系人、跨账号同名、无未读旧会话和仅标题不变而消息区域变化时，识别策略不会串号。
- 验证插件升级/回退、必需登录插件故障、OCR 无密钥运行，以及任何日常路径均不触发进程内存扫描。
